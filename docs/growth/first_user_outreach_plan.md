# First-User Outreach Plan

2-week operational plan to convert the first external users using canonical receipt proof.

---

## Audience Buckets

### 1. Solana Bot Builders (PRIMARY)

**Who:** Developers running trading bots on Solana (MEV, arbitrage, sniper, copy-trade).

**Why they care:**
- Safe execution — policy approves before trade hits chain
- Structured outputs — `bot_line` field and JSON receipt designed for automation
- Canonical receipts — tamper-evident proof of what happened, parseable by machines

**Proof to send:** Bot integration snippet + real receipt with `bot_line` output

### 2. Agent Developers (PRIMARY)

**Who:** Teams building AI agents that execute financial transactions (LangChain, AutoGPT, custom frameworks).

**Why they care:**
- Approval before execution creates a trust boundary for autonomous agents
- Finalization after execution gives agents verifiable proof of outcome
- Receipts are readable for humans, structured for agents

**Proof to send:** Canonical proof example + `finalize_execution` flow

### 3. DeFi Infra Teams (PRIMARY)

**Who:** Teams building execution infrastructure, routing layers, or execution APIs.

**Why they care:**
- Policy enforcement before execution prevents bad trades
- Canonical receipts provide auditable execution history
- Deterministic verification — any party can verify without secrets

**Proof to send:** Canonical receipt launch pack + receipt spec reference

### 4. Protocol Teams (SECONDARY)

**Who:** Solana protocol teams (DEXs, lending, perps) looking for ecosystem integrations.

**Why they care:**
- Trust layer for third-party integrations executing against their protocol
- Structured receipts give protocols visibility into agent-driven volume
- Policy enforcement protects protocol reputation

**Proof to send:** Protected swap example showing Jupiter path + canonical receipt

### 5. Advanced Retail Bot Users (TERTIARY)

**Who:** Power users running their own bots or using bot-as-a-service tools.

**Why they care:**
- One command to protect a trade
- Proof that the trade was checked before execution
- Simple verification of what happened

**Proof to send:** First trade pack (`npx @trucore/atf@1.4.2 trade`)

## Key Messaging Rules

1. Every message anchors to real proof — no future promises
2. Use: "approved before execution", "finalized after execution", "canonical tamper-evident receipt"
3. Avoid: "on-chain anchored", "cryptographically signed", "fully trustless" (not yet shipped)
4. Keep CTAs specific — "run this command", "try one protected trade", "want the bot snippet?"
5. Match message depth to audience — short for bot users, technical for infra teams
