EXACT FAILING ROUTES
====================

RECEIPTS FAILURE
- Route: GET /api/customer/receipts (was calling direct ATF_API_BASE)
- Client fetch: `fetch("${ATF_API_BASE}/customer/receipts", { headers: { Authorization: Bearer token } })`
- ATF_API_BASE target: https://api.trucore.xyz/customer/receipts
- Error thrown: "Failed to fetch receipts" (generic error on any non-200 status)
- Root cause path: lib/customer-auth.ts - fetchReceipts(), fetchReceiptDetail(), verifyReceipt()

VERIFY/QUICK-TEST FAILURE
- Route: POST /api/sandbox/protect (was sending stale payload schema)
- Client request: run-test-request.tsx Quick Test button
- Backend target: /sandbox/protect at ATF backend
- Sample payload problem: using max_slippage_bps instead of slippage_bps
- Error response: 422 Unprocessable Entity
- Root cause path: components/run-test-request.tsx - SAMPLE_INTENT constant

EXACT ROOT CAUSE CLASSIFICATIONS
=================================

RECEIPTS ROOT CAUSE
-------------------
Classification: E (incomplete proxy migration / wrong route)

Details:
- The client code (lib/customer-auth.ts) was directly calling ATF_API_BASE/customer/receipts
- This bypassed the proxy route infrastructure meant to control backend URLs server-side
- The proxy routes existed partially but were incomplete:
  - app/api/customer/receipts/route.ts (GET list) ✓
  - app/api/customer/receipts/[id]/route.ts (GET detail) ✗ MISSING
  - app/api/customer/receipts/verify/route.ts (POST verify) ✗ MISSING
- The incomplete migration left the client making direct backend calls without proper proxy handling
- Error handling was generic ("Failed to fetch receipts") instead of descriptive error codes

VERIFY/QUICK-TEST ROOT CAUSE
-----------------------------
Classification: A (outdated request payload shape)

Details:
- SAMPLE_INTENT in run-test-request.tsx was using outdated field name "max_slippage_bps"
- Backend schema (firewall-api/firewall_api/routes/public_sandbox.py) expects "slippage_bps"
- Pydantic validation on the SandboxProtectRequest model was rejecting the payload
- This resulted in 422 Unprocessable Entity response
- The 422 fallback path presented a "verified example response" to the user
- Root cause was site-side schema mismatch, not backend failure

FALLBACK BEHAVIOR: True Backend Failure Only
==============================================

BEFORE:
- 422 error from stale SAMPLE_INTENT would show fallback "verified example response"
- User was shown fallback on site-side schema mismatch (not a true backend failure)
- Fallback banner implied backend was unavailable when it was actually a client request bug

AFTER:
- SAMPLE_INTENT now sends valid slippage_bps field matching backend schema
- 422 errors should NOT occur in normal operation
- Fallback is only shown for genuine backend failures:
  - Network errors (connection refused, timeout)
  - 500+ server errors (upstream_5xx)
  - 429 rate limit (temporary, expected recovery)
- Client-side schema mismatches no longer trigger fallback pathway
- Error messages are specific and descriptive ("Receipts service is temporarily unavailable" vs generic "Failed to fetch")

Receipts page error scoping:
- Hard error banner only on fetch failures
- Empty state renders cleanly when receipts array is empty (not treated as error)
- Detail view 404 handled gracefully
- Verification failures carry specific codes (not_found, upstream_5xx, unauthorized, etc.)

Quick-test error scoping:
- With corrected payload, normal path succeeds against live backend
- Fallback only appears for:
  - Network connection errors
  - Server 500+ responses
  - Rate limit 429 (with helpful "Please wait" message)
- 422 would indicate a NEW schema mismatch requiring immediate investigation (bugfix, not fallback)
